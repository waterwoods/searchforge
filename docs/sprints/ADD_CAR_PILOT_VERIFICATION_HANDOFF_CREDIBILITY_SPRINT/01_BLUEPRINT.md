# ADD-CAR Pilot Verification + Handoff Credibility Sprint — Blueprint

## Sprint goal

Answer one commercial question: **Is the current Add-Car flagship path credible enough to use in a real pilot with a broker office?** Focus on real-use verification, handoff trust, customer post-submit reassurance, and office-side continuity—not broad product redesign.

## Why now

Prior sprints improved page framing, state, handoff copy, workbench echo, and simulation coverage. The open question is no longer “does the UI look serious?” but **whether a broker and a customer would trust this in real use**. This sprint validates that trust thesis with evidence and honest gaps.

1. `docs/UNIFIED_INTAKE_PRODUCT_AND_TECHNICAL_MASTER_OUTLINE.md` — Stage 1 scope, Add-Car wedge, state-driven direction.
2. `docs/PROJECT_TRUTH_SWITCH.md` — canonical paths, persistence/ops truth, edit-risk map.
3. `docs/sprints/ADD_CAR_INDUSTRIAL_SCORECARD_V1_SPRINT/02_ADD_CAR_INDUSTRIAL_SCORECARD_V1.md` — PAGE/FLOW/STATE/HANDOFF scores and gaps.
4. `docs/sprints/ADD_CAR_INDUSTRIAL_SCORECARD_V1_SPRINT/03_FINAL_REPORT.md` — consolidated scorecard outcome and recommended follow-ups.

## Scope

- Realistic Add-Car verification (happy path, materials/already-sent, clarification).
- Handoff and post-submit credibility (copy, engine behavior, workbench alignment by code review).
- Pilot/commercial readiness vs “good demo.”
- Small, bounded copy/config fixes only if a clear pilot blocker is found.

## Non-scope

- Full UI redesign, CRM expansion, carrier APIs, deployment changes, large new doc sets, abstract platform architecture.

## Target outcome

A clear **pilot-readiness judgment**: what is credible today, what is weak, what must be validated with a real broker vs fixed in product, and a single recommended next sprint focus.
