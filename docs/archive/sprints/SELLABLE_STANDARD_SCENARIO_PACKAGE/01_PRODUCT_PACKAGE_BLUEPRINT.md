# Product Package Blueprint — Sellable Standard Scenario Package Sprint

**Purpose:** Explain why a sellable standard scenario package matters now, what this sprint strengthens, and what it intentionally will not do.

**Scope:** SearchForge → Chen Kui Insurance Unified Entry

**Created:** 2026-03-17 — Sellable Standard Scenario Package Sprint

---

## 1. Why a Sellable Standard Scenario Package Matters Now

The product has evolved through many sprints: backbone, scenario hardening, multi-turn continuity, workflow_state, case handoff, broker workbench. It is **strong** in many areas.

But **strong ≠ sellable**.

To move from "a strong evolving MVP" toward "a sellable standard scenario package," the product must:

1. **Be explainable clearly** — A prospect knows what they get in one sentence.
2. **Be demonstrable** — The founder can show the package in 5–10 minutes.
3. **Be reusable** — Similar brokers can adopt it with limited adaptation.
4. **Be commercially coherent** — The included scenarios feel like a real offer, not a grab bag.

---

## 2. Why This Is the Correct Move After Backbone + Scenario Hardening

| Prior phase | What it built | What we now need |
|-------------|---------------|-------------------|
| Backbone | Minimal production backbone, persistence, routing | **Package clarity** — what is in the bundle |
| Scenario hardening | 3–5 turn flows, add-car, claim, renewal, missing-doc | **Package coherence** — what belongs together |
| Workbench | Case queue, status, follow-up, reopen | **Office-side packaging** — what the broker gets |
| Handoff | Collected, Still needed, broker_next_step | **Handoff packaging** — what makes handoff sellable |

The product is not missing features. It is missing **packaging**.

---

## 3. What This Sprint Will Strengthen

| Area | Strengthening |
|------|---------------|
| **Package definition** | Clear name, target user, included scenarios, in-scope vs deferred |
| **Scenario coherence** | Which scenarios belong together; why they form a commercial offer |
| **Office-side value** | What the broker sees as part of the package; workbench as part of the offer |
| **Handoff packaging** | What makes handoff commercially useful; how it reduces manual follow-up |
| **Founder demo / sales clarity** | What to inspect; what to say; which scenarios best demonstrate |

---

## 4. What This Sprint Will NOT Do

| Intentional non-goal | Reason |
|---------------------|--------|
| Add broad new functionality | Sprint is about packaging, not building |
| Enterprise generalization | Target is small broker / small merchant |
| Make every scenario perfect | Package coherence > individual perfection |
| Platform work | No multi-tenant, auth, Stripe, CRM |
| Giant refactor | Tighten existing, not rebuild |

---

## 5. Core Principle

**Do NOT average effort across too many new features.**  
**Do NOT drift into giant platform work.**  
**Do NOT improve one scenario in isolation.**

This sprint is about:
- **Standardizing** the most commercially valuable scenario set
- **Packaging** what already works into a clearer offer
- **Tightening** the weakest packaging gaps
