# UI Productization Blueprint

**Sprint:** UI Productization / Trial UI Polish  
**Scope:** SearchForge → Chen Kui Insurance Unified Entry  
**Target:** 45–90 minutes

---

## 1. Why UI Productization Matters Now

The product has a strong functional backbone:
- Customer Entry with multi-turn continuity
- Scenario package and case handoff
- Broker Workbench with queue, status, follow-up memory
- Trial package and launch checklists

**The main gap is not functionality.** The main gap is:
- **Clarity** — users should immediately understand what to do
- **Trust** — the product should feel professional, not experimental
- **Visual hierarchy** — primary actions and key info should stand out
- **Product feel** — reduce "this is still a test/demo tool" perception

Before real broker trial, the founder correctly wants the UI to feel more professional and product-like. A broker or small business customer should see a tool they would use daily, not an internal MVP.

---

## 2. Why This Is the Correct Move Before Real Trial

- **First impression matters:** A cluttered or debug-like UI undermines trust in the underlying capability.
- **Demo confidence:** The founder needs to show the product without apologizing for the interface.
- **Trial adoption:** Brokers are more likely to adopt a tool that looks finished and trustworthy.
- **Low risk:** This sprint does not change behavior or logic—only presentation and clarity.

---

## 3. What This Sprint Will Strengthen

| Area | Target |
|------|--------|
| 1. Welcome area | Clearer, more reassuring first message |
| 2. Button hierarchy | Primary actions obvious; secondary actions de-emphasized |
| 3. Example visibility | Examples easy to find but not overwhelming |
| 4. Chat layout | Cleaner bubbles, clearer role labels |
| 5. Case summary visibility | Above-the-fold, scannable |
| 6. Next move visibility | Prominent "Your next move" block |
| 7. Workbench card readability | Clearer tags, grouping, spacing |
| 8. Empty states | Helpful, not generic |
| 9. Section naming | Product-like labels, not internal jargon |
| 10. Demo/trial path | Founder demo path looks polished |

---

## 4. What This Sprint Will NOT Do

- **No broad redesign** — Keep current layout and flow
- **No new features** — No new functionality
- **No branding overhaul** — No logo, color system, or theme overhaul
- **No decorative-only work** — Every change must improve clarity or trust
- **No backend changes** — UI-only changes

---

## 5. Success Criteria

At the end of this sprint:
- Entry experience feels clearer and more welcoming
- Workbench feels more like a real operational tool
- Demo/trial path feels more polished
- Founder can show the product to a broker with confidence
- Less "debug screen" feeling; more "product" feeling
